A Mock Technical Interview for Data Analysts: SQL, Python, and Designing an A/B Test

August 2026 · 14 min read

In the previous article I summarized the five stages of the data analyst hiring process I went through, and the types of use cases that came up. Now I want to reconstruct the technical interview as a dialogue, so the flow is easier to picture. This isn't a word-for-word transcript, but it's rebuilt from notes I took right after the session, so the flow is representative of what actually happened.

The interviewer was a Lead Data Analyst from the relevant team. The session ran about an hour, split into SQL, Python, then A/B testing and causal inference. I've added notes in a few places to explain what was actually being tested.

Part 1: SQL

Interviewer: "Okay, I'll give you two tables. The first is called city_cost, with columns date, channel, city, and cost. The second is called order_rev, with date, channel, city, order_id, and revenue. Calculate ROI by date and channel. ROI is revenue divided by cost."

Me: "Before I write the query, can I check the grain of each table first? From the column names, city_cost looks like it's already at the date-channel-city level, but order_rev has an order_id, so it's probably at the order level, not date-channel-city."

Interviewer: "Correct. Why does that matter?"

Me: "Because if I JOIN these two tables as they are, one row in city_cost could match many rows in order_rev. Revenue would get counted multiple times, so the resulting ROI could come out much higher than it actually is. The right approach is to aggregate order_rev to the date-channel-city grain first, SUM(revenue), then JOIN it to city_cost, which is already at that same grain."

Note: this opening question looks simple but is actually a classic grain trap. The interviewer didn't need me to jump straight into writing a query. What they're looking for is whether I pause to check the data structure first, instead of reflexively joining two tables as-is.

Interviewer: "Good. Now, what if there's a row with revenue but the cost is zero, or even NULL?"

Me: "Those two conditions mean different things, so I'd check with the data team before handling them blindly. Zero cost most likely means organic traffic, genuinely no spend on that channel. NULL cost usually signals missing data, either a pipeline that hasn't run yet or some tracking issue. For the ROI calculation, if cost is zero, I wouldn't let the result come out as infinity. I'd set ROI to NULL or flag it specifically, so it doesn't get misread as an unusually strong-performing channel."

Interviewer: "Okay, last one for SQL. Get the two highest-ROI days for each channel."

Me: "I'd use a CTE. First step, calculate daily ROI per channel inside the CTE. Second step, in the outer query, use a window function, PARTITION BY channel, ORDER BY ROI descending, ROW_NUMBER if I need exactly two rows per channel, or RANK if there are tied ROI values that should be allowed to appear more than twice. Finally, filter for rank less than or equal to two."

Interviewer: "Why ROW_NUMBER over RANK?"

Me: "Depends on the requirement. If the requirement is strictly two rows per channel regardless of ties, I'd use ROW_NUMBER. If there are two days with exactly the same ROI and both should be treated as equally important, I'd use RANK, even if that ends up returning more than two rows for a channel."

Part 2: Python

Interviewer: "Write a Python function that returns all divisors of a number n. For example, n = 15 should return [1, 3, 5, 15]."

Me: writes roughly the following while explaining each line.

"I define a function with one parameter, n. Inside, I set up an empty list to hold the results. I loop i from 1 to n, and at each iteration I check whether n modulo i equals zero, if so, i is a divisor, and I append it to the list. Finally I return the list."

Interviewer: "Can you explain the modulo line again, why is that what's used to check for a divisor?"

Me: "Modulo gives you the remainder of a division. If n divided by i leaves a remainder of zero, that means i divides n evenly, so i is indeed a divisor of n. If the remainder isn't zero, i isn't a divisor."

Interviewer: "Can it be optimized?"

Me: "Yes. Right now I'm looping all the way to n, but divisors always come in pairs. If i is a divisor of n, then n divided by i is also a divisor. So I only need to loop up to the square root of n, and every time I find an i that's a divisor, I also add n divided by i to the list, except when both are equal, which happens at the exact square root."

Note: this follow-up is actually more important than the code itself. The interviewer wasn't too concerned with whether I had the exact syntax memorized. What's being assessed is whether I can explain the logic clearly and recognize the inefficiency in my own first solution.

Part 3: A/B Testing and Causal Inference

Interviewer: "Now a case study. There's a registration funnel with several steps, and we're seeing a lot of drop-off in the middle step. The idea: if a user has no activity for two hours, send an automated call as a reminder. The goal is to increase registrations. How would you design the experiment?"

Me: "I'd start with a hypothesis: the reminder call will increase funnel completion rate, specifically the transition from that drop-off step to the next one. The population is users who've reached that step but haven't progressed after two hours, and meet the eligibility criteria to be contacted. I'd randomize that population into treatment, which receives the call, and control, which gets the regular communication or nothing at all."

"For the primary metric, I'd use incremental funnel completion rate, not call pickup rate or click-through rate. The business objective is registration, not how many people pick up the phone. Secondary metrics would be conversion between steps and time to completion. Guardrails I'd monitor: complaints, opt-outs, cost per call, and any sign of negative user experience."

Interviewer: "Good. Now imagine user volume is low, and the MDE you want requires a sample size larger than the available population. What do you do?"

Me: "I wouldn't just say run it longer, because if the population is genuinely small, more time might not fix the problem. First I'd validate whether the MDE I set is actually realistic and business-meaningful, maybe I need to widen it. I'd also consider pooling comparable markets to get a larger population, or using sequential testing or a Bayesian approach that can produce a decision earlier with limited data. If it turns out to be statistically impossible to reach adequate power, I'd communicate that limitation explicitly to stakeholders, rather than pretending the result is conclusive."

Interviewer: "Say the results do show an uplift. How do you decide whether it's worth rolling out?"

Me: "I wouldn't stop at 'the result is statistically significant.' I'd calculate incremental registrations from treatment, then cost per incremental registration. For example, if treatment produces 100 incremental registrations at an additional cost of five thousand euros, that's fifty euros per incremental registration. I'd compare that against the economic value of a single registered user, and only then could I say whether it's worth rolling out."

Interviewer: "Last one, how do you know a booking increase is actually because of the campaign, and not something else?"

Me: "Here I'd first separate attribution from causal inference. Attribution is about who gets credit for a booking. Causal inference is about what would have happened if the campaign hadn't run, the counterfactual. The most solid way to get a counterfactual is a randomized experiment with a holdout group. If that's not feasible, there are alternatives like geo experiments, matched controls, difference-in-differences, or synthetic control."

Interviewer: "Is causal inference something you build into the pipeline, or handle ad hoc?"

Me: "Depends on the scale of the campaign. For routine campaigns with a smaller budget, standardized attribution and monitoring are enough, not everything needs sophisticated causal inference. But for strategic campaigns with a bigger budget, I'd go deeper, using a holdout group and causal analysis, because the decisions coming out of that carry much bigger consequences."

Closing note: throughout this A/B testing section, the pattern I noticed was that the interviewer kept digging one level deeper than my previous answer. A good answer isn't the longest one, it's the one that still holds up when pushed with "and how do you know that's true?"

Closing Thoughts

What I realized once this session ended: a senior-level technical interview isn't really testing whether you can write a query or code that runs. That's treated as the baseline. What's actually being tested is whether you pause to think before answering, and whether you can hold your logic together when pushed further.
